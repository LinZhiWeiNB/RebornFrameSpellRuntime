# 属性请求流水线

本文是资源当前值请求的下一代合同。它还没有替换已经实现的封存、监听系统组和结算。修改器阶段见 [属性修改器设计](属性修改器设计.md)。Buff 与属性的 tick 顺序见 [Buff系统](Buff系统.md)。

一个 World 只有一条 `AttributePipeline`。`UpdateOnce` 仍由上层锁步在主线程、非重入地调用。批次期间不得 Disabled、Destroy 或回收已经进入流水线的单位。

## 结论

本帧要结算的请求在封存时固定。监听器由 Buff 创建，上面放条件表达式、一组 `BuffEffectBase`，以及每个效果自己的 `IMessage`。条件是否成立不在本文讨论。

条件成立时，监听器仍调用现有的 `Execute(in BuffEffectContext, IMessage)`。`IMessage` 用监听器保存的那份。`BuffEffectContext` 在这次调用里带上当前引用：请求监听阶段是这一条热请求，结算事件监听阶段是这一条已发布事件。同一次调用只带其中一种。效果子类如何使用这个引用，由项目自己决定。

单位局部监听按单位并行。跨单位监听在全部分部监听完成之后，于主线程按注册顺序串行。结算在全部请求监听之后，再按单位并行。结算事件监听在事件发布之后。

## 相对讨论稿的取舍

讨论稿里的封存封闭、单位内串行结算、跨单位效果延迟一帧、按 `SpellStableId` 消除提交时序，这些保留。下面这些不采用。

| 讨论稿 | 本合同 |
| --- | --- |
| 监听器直接创建下一帧的属性请求 | 框架不规定效果的写入方式。效果通过上下文上的当前引用处理这一条热请求或结算事件，其余行为由子类实现。 |
| 存在全局监听器时，监听整体改为主线程串行 | 局部监听始终按单位并行。跨单位监听是后面的独立阶段，不把局部监听拖回串行。 |
| 局部监听和结算放进同一个单位作业 | 监听全部结束后才结算。跨单位监听要在结算前看见并可能改写热请求。托管监听器也不能放进 Burst 作业。 |
| 单位实体不再内联缓冲，每帧换成一套平行内存块 | 持久状态仍放在现有实体缓冲上。热区是 World 工作区里的本批快照，做法和修改器的 `CalcInput` 相同。 |
| 排序后重新分配 `RequestId`，排序键含 phase | `RequestId` 仍在提交时按目标单位分配，供 Tag 和事件标识使用。排序只分配本批 `SettleIndex`。排序键是 `(SourceStableId, SourceSeq)`，不加 phase。 |
| 热区放入不致死、护盾池等结算字段 | 第一版标志只有取消和拒绝。不致死、护盾、分摊是以后的结算标志或 Buff，不进这版数据结构。 |
| 死亡单位的 Pending 在清空、尸体结算、转移给击杀者里三选一 | 只保留现有规则：批次之间由同步清理丢掉该单位尚未封存的请求，不转移。 |

## 一帧在算什么

封存完成之后，这一帧的请求结算是：

```text
(本批热请求, 修改器写回后的属性快照, 监听器上的效果) -> (新的 Current, 本批事件, 效果自己提交的后续请求)
```

由此确定：

- 请求监听阶段，上下文引用的是流水线正在处理的那一条热请求，不是一份拷贝，也不是整个 Pending 缓冲。
- 结算事件监听阶段，上下文引用的是刚刚发布的那一条 `AttributeResolvedEvent`。
- 局部监听阶段，这个引用只可能指向本单位的请求或事件。
- 请求监听读到的 Current 是修改器写回之后、请求结算之前的值。结算事件监听才看得到本帧写回结果。
- 效果子类可以改这条热请求，也可以再提交别的请求。框架不替子类规定改哪些字段。
- 可观察结果不能依赖实体索引、Chunk 顺序或线程完成顺序。

每个逻辑 tick 的调用顺序不变：

1. `BuffPipeline.UpdateOnce(logicTick)`。
2. `AttributePipeline.UpdateOnce()`。
3. 单位 Disabled、Destroy 或回收。

属性监听器在第 2 步写入的 Buff Pending，要到下一个 tick 的第 1 步才分发。效果里的 `TryRequestCurrentValue` 进入属性 Pending，并在同一个下一 tick 的第 2 步封存。中间不把两条流水线再跑一遍。

## 监听器

监听器不是独立注册的属性系统，而是 Buff 创建出来的对象。它保存三样东西：条件表达式、一组 `BuffEffectBase`、每个效果对应的 `IMessage`。条件表达式尚未实现，本文不定义它。

`IMessage` 只放在监听器上。`BuffEffectContext` 不保存参数消息。监听器调用效果时，把自己保存的那份传给现有入口：

```csharp
effect.Execute(context, listener.ParametersFor(effect));
```

效果实例仍按类型共用，不能把当前请求或参数存在效果对象上。

`BuffEffectContext` 增加两个调用期引用。同一次 `Execute` 最多有一个有效：

| 阶段 | `PendingAttributeChange` | `ResolvedAttributeEvent` |
| --- | --- | --- |
| Buff 生命周期分发 | 无 | 无 |
| 属性请求监听 | 当前这一条热请求 | 无 |
| 结算事件监听 | 无 | 当前这一条已发布事件 |

引用指向工作区里的那一条记录。请求监听里它就是即将结算的热请求，子类改它会进入后续结算。事件监听里它就是已经编号的结算事件。流水线按一条请求或一条事件绑定一次上下文，再把这个上下文交给监听器；效果自己不去 Pending 或事件缓冲里查找。

监听器分成两类，分类写在监听器上，用来决定流水线能不能把它和别的单位并行：

- 单位局部：保证不检查、不修改其他单位的热请求。流水线只把本单位的那一条请求或事件放进上下文。
- 跨单位：需要看见其他单位的热请求或结算事件。全部单位局部监听结束后，在主线程按 Buff 实例的稳定顺序串行执行。

两类都走同一个 `BuffEffectContext` 和同一个 `Execute`。差别只是流水线允许把哪一条记录绑进上下文。子类拿到引用之后做什么，框架不再包一层专用方法。

## 数据

### 实体上继续保留的状态

这些缓冲和组件保持现有归属，单位初始化时创建：

| 数据 | 作用 |
| --- | --- |
| `AttributeValueSlot` | 持久的 Default、Base、Current、Max。结算最后把新的 Current 写回这里。 |
| `PendingAttributeCurrentValueRequest` | 两次批次之间的冷请求。封存时搬走。 |
| `PendingAttributeRequestTag` | 冷请求上的原因 Tag 和取消 Tag。 |
| `AttributeRequestEventSequence` | 目标单位上的 `RequestId` 计数器。另外增加来源序号计数器。 |
| `AttributeResolvedEvent` 与 `AttributeResolvedEventTag` | 本批事件。消费窗口结束后清空。 |
| `SpellStableId` | 已经存在的业务稳定 ID。0 无效，战斗内不复用。 |

`AttributeCurrentValueRequest` 增加两个只读字段：`SourceStableId` 和 `SourceSeq`。`RequestId` 仍是目标单位内的持久 ID，提交时分配，封存和排序都不改它。

现有不带 `sourceStableId` 的 `TryRequestCurrentValueChange` 继续可用。这种请求把目标单位当作来源，并用来源单位上的来源序号。显式来源使用新的重载。Buff 效果提交当前值请求时，来源写成该效果的 `SourceStableId`，序号从该来源单位的计数器分配。

### 工作区热区

每个 World 一个工作区实体，模式与 `AttributeModifierWorkspace` 相同。热区只在 `UpdateOnce` 内有效，容量按本批实际数量预留，帧末把长度清零、容量留下。

| 缓冲 | 内容 |
| --- | --- |
| `AttributePendingUnit` | 至少有一条冷请求的单位。只在冷请求从空变为非空时追加。 |
| `AttributeWorkUnit` | 本批真正有请求的单位，封存时从上一张表换过来。 |
| `AttributeSnapshotSlot` | 修改器写回之后复制的 Current、Max，按 `SpellStableId` 排序。监听期间只读。 |
| `AttributeHotRequest` | 本批请求的连续数组：目标单位、槽位、`DeltaBits`、`RequestId`、`SourceStableId`、`SourceSeq`、`SettleIndex`、标志。 |
| `AttributeHotEvent` | 与热请求同长、同下标。结算时写入种类和新的 Current。 |

冷数据不进结算循环。属性 ID、值类型、Default、Base、原因 Tag 和取消 Tag 留在实体缓冲里。结算前的预处理把「取消集合非空」和「变化量不合法」收成热请求上的标志，结算循环不再扫描 Tag。

`AttributeSnapshotSlot` 必须在并行监听开始前复制完成。局部监听跑在工作线程上，不能调用 `EntityManager`。快照在请求监听期间保持不变，因为结算还没开始。上下文给出的热请求引用指向这份工作区里的对应元素，所以子类对 `DeltaBits` 和 Tag 的修改留在本单位的热请求上。

### 排序键

封存之后，每个单位把自己的热请求排成：

```text
(SourceStableId, SourceSeq)
```

`SourceStableId` 是 `SpellStableId`，不是实体索引，也不是 Chunk 顺序。同一来源内的 `SourceSeq` 保持该来源的提交顺序。不同来源按稳定 ID 排列，因此调用方谁先碰到目标不再影响结算顺序。

这会改变现有行为。今天同一目标上的请求按提交顺序结算，而提交顺序就是 `RequestId` 的顺序。改完之后，来源稳定 ID 较小的请求先结算。只有一个来源，或者所有请求都使用「来源等于目标」的旧重载时，顺序与现在一致。

排序后的下标加 1 写入 `SettleIndex`，本批、本单位内从 1 连续编号。`RequestId` 不在这里分配。

## 生命周期

### 帧间提交

主线程在两次 `UpdateOnce` 之间调用 `TryRequestCurrentValueChange`。校验仍然同步完成：必须是资源属性，变化量必须符合值类型，原因 Tag 必须已经在目录里。

通过之后：

1. 在来源单位上分配 `SourceSeq`。序号耗尽时从 1 重新开始，0 保留为无效。
2. 在目标单位上分配 `RequestId`。规则与现在的 `AttributeRequestEventSequence` 相同。
3. 把请求和 Tag 写入目标的 Pending。
4. 该目标的 Pending 从空变为非空时，把单位追加到 `AttributePendingUnit`，并记下已经登记。

登记列表的顺序不影响结果。提交不写热区。

### 封存

```text
把 AttributePendingUnit 换成 AttributeWorkUnit
对工作单位：
    把 Pending 请求和 Tag 复制到热请求
    清空 Pending 的长度，保留容量
    清除登记标记
清空旧的登记列表
```

封存之后的新提交进入新的 Pending，不会回到本批。没有请求的单位不进入工作列表。单位已经在批次之间被清理掉时，封存跳过它。

复制完成后，每个工作单位按 `(SourceStableId, SourceSeq)` 排序并写入 `SettleIndex`。这一步只读本单位的热请求，可以按单位并行。

### 修改器

保持 [属性修改器设计](属性修改器设计.md) 的 Seal、Calc、Apply。Apply 把 Base、Max 和缩放后的 Current 写回实体，并留下重算草稿。修改器若读取其他单位，只能读本阶段开始时已经固定的贡献和数值，不能读本批热请求。

修改器 Apply 完成之后，再复制 `AttributeSnapshotSlot`。请求监听和请求结算都使用这份快照作为本帧属性的起点。

### 局部监听

工作项是一个单位。对该单位的每条热请求，流水线把 `BuffEffectContext.PendingAttributeChange` 绑到这一条，再按 Buff 实例的稳定顺序调用这个单位上的局部监听器。监听器在条件通过后，用自己保存的 `IMessage` 依次执行效果列表。

这个阶段的上下文不引用其他单位的热请求，也不引用结算事件。单位之间没有共享的 Current。

### 跨单位监听

全部局部监听结束后进入主线程。流水线仍然一次只绑定一条热请求，但可以绑定其他单位的热请求。跨单位监听器按 Buff 实例的稳定顺序串行执行，因此能看见局部监听已经改过的热请求。`IMessage` 仍然来自监听器自己。

### 预处理和结算

全部监听结束后，按单位并行做两件事。

预处理扫描该单位的取消 Tag 和变化量，把结果写成热请求标志：

| 标志 | 含义 |
| --- | --- |
| `Cancel` | 取消集合非空。结算不写 Current。 |
| `Reject` | 监听器把变化量改成了该值类型不接受的原始值。结算不写 Current。 |

结算按 `SettleIndex` 逐条执行，不能拆开，也不能换成与顺序无关的求和：

1. 标志含 `Cancel` 或 `Reject` 时，只留下对应事件。
2. 否则用 `WideMath` 把当前 Current 和 `DeltaBits` 相加。`Fixed64` 走现有的定点加法。
3. 把结果限制到 `0` 和 Max 之间。Max 使用修改器写回后的值；请求结算不重新计算 Max。
4. 限制后与旧值相同，事件种类为 `RequestNoChange`；否则写回热区 Current，种类为 `RequestApplied`。
5. 每条请求都留下事件，包括取消、拒绝和无变化。

后一条请求看见前一条已经写回的 Current。工作项结束时，把热区 Current 写回该单位的 `AttributeValueSlot`。

### 事件

单位内把重算草稿和请求事件一起排序。请求事件的键是：

```text
(AttributeId, SettleIndex)
```

同一属性上，这个顺序就是结算顺序。重算草稿的 `RequestId` 为 0，排在同一属性的请求事件之前；同一键下 Max 仍在 Current 之前。排序后分配本批、本单位内从 1 开始的 `EventId`，并把原因 Tag、取消 Tag 复制到事件 Tag。Tag 复制使用原来的 `RequestId`。

事件缓冲仍放在单位上。跨单位遍历事件时，按 `SpellStableId` 遍历 `AttributeWorkUnit`，不使用实体查询顺序。

### 结算事件监听

事件发布之后、清空之前，流水线对每条已发布事件再跑一轮监听。这次 `BuffEffectContext.ResolvedAttributeEvent` 指向这一条事件，`PendingAttributeChange` 为空。

单位局部的事件监听仍按单位并行，上下文只引用本单位的事件。跨单位的事件监听在局部完成之后，于主线程按 Buff 实例的稳定顺序串行执行。监听器同样用自己保存的 `IMessage` 调用 `Execute`。这个阶段热请求已经结算完，效果再提交的属性请求或 Buff 请求进入下一帧的 Pending。

## 并行

| 阶段 | 执行位置 | 写入范围 |
| --- | --- | --- |
| 冷请求登记 | 主线程 | 目标 Pending，以及从空变为非空时的登记列表 |
| 封存和单位内排序 | 可按单位并行 | 本单位热请求 |
| 修改器 Calc / Apply | 维持现有作业 | 现有工作区和本单位属性 |
| 属性快照 | 屏障之后 | 工作区快照 |
| 局部请求监听 | 每单位一个工作项，单位内按热请求逐条绑定 | 上下文只引用本单位当前热请求 |
| 跨单位请求监听 | 主线程，Buff 实例稳定顺序 | 上下文可引用任意单位的一条热请求 |
| 预处理和结算 | 每单位一个 Burst 作业 | 本单位热区 Current、热事件，并写回本单位属性槽 |
| 事件编号 | 每单位局部完成 | 本单位事件缓冲 |
| 局部事件监听 | 每单位一个工作项，单位内按事件逐条绑定 | 上下文只引用本单位当前结算事件 |
| 跨单位事件监听 | 主线程，Buff 实例稳定顺序 | 上下文可引用任意单位的一条结算事件 |

局部监听是托管虚方法，使用按单位隔离的工作项，不使用 Burst。预处理和结算没有托管调用，使用 `IJobParallelFor`，一个工作项处理一个单位。作业在当次 `UpdateOnce` 内 `Complete`。

`EntityManager` 只在主线程使用。工作线程只读写工作区里预先切好的区间。

## 批次顺序

`AttributePipeline.UpdateOnce` 的目标顺序：

| 顺序 | 阶段 |
| --- | --- |
| 1 | 封存冷请求，单位内按来源排序并分配 `SettleIndex` |
| 2 | 修改器 Seal、Calc、Apply |
| 3 | 复制修改器写回后的属性快照 |
| 4 | 按单位并行做局部请求监听。每条热请求绑定一次 `PendingAttributeChange` |
| 5 | 主线程串行做跨单位请求监听 |
| 6 | 按单位并行预处理标志并结算，写回 Current |
| 7 | 单位内排序草稿、分配 `EventId`、复制 Tag |
| 8 | 按单位并行做局部结算事件监听。每条事件绑定一次 `ResolvedAttributeEvent` |
| 9 | 主线程串行做跨单位结算事件监听 |
| 10 | 清空已发布事件，清掉本批热区长度 |

第 8 步和第 9 步替换现在的 `AttributeEventConsumerSystemGroup`。效果在这里提交的修改器、属性请求和 Buff 请求进入下一帧相应的 Pending，不再改本批热请求。

`AttributeRequestListenerSystemGroup` 同时移除。业务不再把 `ISystem` 加进这两个组，而是由 Buff 创建监听器。

## 跨单位效果怎么表达

| 效果 | 表达 |
| --- | --- |
| 同帧减伤、加伤、免疫、取消 | 请求监听里，子类改上下文引用的那条热请求 |
| 持续光环 | 由 Buff 维护修改器，或由效果自己提交后续请求 |
| 要看本帧结算结果再行动 | 结算事件监听里，子类读上下文引用的那条 `AttributeResolvedEvent` |
| 必须看其他单位的热请求或结算事件 | 监听器标成跨单位，在对应的串行阶段执行 |

精确地按其他单位本帧结算后的剩余生命分配伤害，不在本帧做。那需要读结算后的 Current，而结算与其他单位并行，且本帧输入已经封闭。

## 确定性

各端必须一致：

1. 热请求按 `(SourceStableId, SourceSeq)` 排序。`SourceStableId` 使用 `SpellStableId`。
2. `RequestId` 在目标单位提交时分配，之后不变。`SettleIndex` 在排序后分配。
3. 单位内结算严格按 `SettleIndex` 串行。
4. 单位内事件按 `(AttributeId, SettleIndex)` 排序，重算事件在同一属性的请求事件之前，Max 在 Current 之前。
5. 同一单位上的监听器按所属 Buff 实例的 `SpellStableId` 和实例 ID 排序，不按线程完成顺序、实体索引或 Chunk 顺序。
6. 加法使用现有 `WideMath` 和 `Fixed64`，最后限制到 `0` 与 Max。
7. 局部监听的上下文只引用本单位的当前热请求或当前结算事件。跨单位引用只出现在随后的主线程阶段。
8. 效果不能调用 `UpdateOnce`。事件监听阶段再提交的请求进入下一帧。
9. 批次之间移除单位时，同步清理丢掉它的 Pending，并从登记列表撤下。不把这些请求转移给其他单位。
10. 修改器阶段不读本批热请求。
11. 工作线程不扩容共享容器。
12. 哈希和集合只用于成员判断，不按它们的迭代顺序输出事件或请求。

并行结果与「按稳定 ID 排列单位，再按单位内 `SettleIndex` 执行」的单线程结果一致。一致的是每个单位的 Current、事件，以及效果在确定顺序下提交的后续请求，不是工作区容量、内部分配器地址或线程完成顺序。

## 实现范围

替换请求半段时，主要落点是：

- `Runtime/Attribute/AttributeAccess.cs`：来源序号、显式来源，以及 Pending 从空变为非空时登记。
- `Runtime/Attribute/AttributeComponents.cs`：请求上的来源字段，工作区热缓冲。
- `Runtime/Attribute/AttributeInputSealSystem.cs`：只封存登记过的单位，并排成 `SettleIndex`。
- `Runtime/Attribute/AttributeRequestSystems.cs`：监听之后按 `SettleIndex` 结算。
- `Runtime/Attribute/AttributeEventPublishSystem.cs`：事件键改为 `SettleIndex`。
- `Runtime/Attribute/AttributePipeline.cs` 与 `AttributeSystemGroups.cs`：按本文的顺序编排，移除监听系统组。
- `Runtime/Buff/BuffEffectSystems.cs`：`BuffEffectContext` 增加当前热请求引用和当前结算事件引用。Buff 生命周期分发时两者都为空。
- 监听器由 Buff 创建，并保存每个效果的 `IMessage`。属性流水线只负责绑定引用和调用监听器。
- `Tests/Runtime/Attribute/AttributePipelineTests.cs`：来源顺序、局部上下文不引用其他单位、请求监听与事件监听拿到的是不同引用。

第一版不实现不致死标志、护盾池、链式深度限制和全局仇恨表。这些继续由 Buff 或以后的结算标志表达。
